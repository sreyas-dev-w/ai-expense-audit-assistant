# Change Process

Rules for safely changing architecture-critical areas.

## Changes to the Agent Workflow

Changes to the LangGraph workflow are **architectural changes**.

Before modifying the workflow, understand:

```text
Input
  ↓
Graph State
  ↓
Node / Agent
  ↓
Tool Calls
  ↓
Structured Output
  ↓
Next Node
  ↓
Persistence
```

When adding or removing an agent, consider:

- input/output contracts
- state changes
- failure behavior
- persistence requirements
- tool requirements
- downstream dependencies
- grounding requirements

**Do not add an agent simply because a piece of logic could theoretically be represented as one.** Use normal,
deterministic application code for deterministic operations.

## Database Changes

When modifying database models:

1. Update the SQLAlchemy model.
2. Determine the required schema migration.
3. Create/update the Alembic migration.
4. Verify constraints and indexes.
5. Consider existing data and migration safety.
6. Verify application queries affected by the change.

**Never assume that changing a SQLAlchemy model automatically changes the database.**

## RAG Changes

When modifying the policy RAG pipeline, consider the complete stage path (ingestion → chunking → embedding →
storage → retrieval → reasoning) and how a change in one stage affects the others. See
`docs/backend/rag-pipeline.md`.

Do not optimize retrieval solely for similarity score; relevance and sufficient grounding context matter more.

## Review Checklist

- [ ] Data contracts updated where inputs/outputs changed?
- [ ] Failure behavior defined for every new node/tool?
- [ ] Alembic migration created for any schema change?
- [ ] Migrations reviewed (not blindly autogenerated)?
- [ ] Transaction boundaries respected (no long open transactions)?
- [ ] Secrets/config handled via environment, never committed?
- [ ] No new architectural dependency without a documented decision?
