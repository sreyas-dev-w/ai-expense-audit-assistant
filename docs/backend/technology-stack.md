# Technology Stack

Standards for the backend technology stack. Use these technologies and conventions unless there is a documented
reason to deviate.

## FastAPI

Use FastAPI for HTTP APIs.

Prefer:

- typed request and response models
- dependency injection
- async endpoints
- clear separation between routing and application logic
- Pydantic validation

Avoid putting database queries, complex business logic, or agent orchestration directly inside route handlers
(see `docs/backend/api-design.md`).

## Pydantic

Use Pydantic models for structured application and agent data.

Pydantic models define contracts between:

- API requests and responses
- agents
- agent tools
- services
- persistence boundaries where appropriate

Agent communication must use explicit structured models rather than loosely defined dictionaries or free-form
strings. Example:

```python
class ValidationResult(BaseModel):
    is_valid: bool
    violations: list[str]
    warnings: list[str]
```

The exact models belong to the relevant domain and evolve with the application. **Do not duplicate the same
conceptual schema in multiple locations** (see `docs/schemas/data-contracts.md`).

## SQLAlchemy

Use the **latest stable SQLAlchemy 2.x API**. Prefer modern patterns:

```python
class ExpenseClaim(Base):
    __tablename__ = "expense_claims"

    id: Mapped[UUID] = mapped_column(primary_key=True)
    amount: Mapped[Decimal] = mapped_column(...)
```

Use:

- `Mapped`
- `mapped_column`
- SQLAlchemy 2.x query style
- typed ORM models
- explicit relationships
- async SQLAlchemy where database operations are asynchronous

Avoid legacy SQLAlchemy APIs when an equivalent modern API exists. **Do not introduce a second ORM.**

## PostgreSQL

The production database is **PostgreSQL**. PostgreSQL-specific functionality may be used when it provides a
meaningful benefit. Database design should prioritize:

- correct constraints
- appropriate indexes
- normalized relational data where appropriate
- explicit relationships
- transactional integrity
- predictable query performance

**Do not move relational data into JSON fields simply because JSON is convenient.** Use JSON/JSONB only when the
data is genuinely semi-structured or there is a clear architectural reason.

## psycopg

Use **psycopg 3** as the PostgreSQL driver. The SQLAlchemy PostgreSQL connection should use the psycopg dialect.

Do not introduce `psycopg2` unless there is a specific, documented compatibility requirement.

## Database Sessions

Database access uses properly managed SQLAlchemy sessions. Prefer async database access for the async FastAPI
application.

Sessions must be:

- created through the application's configured session factory
- scoped appropriately
- closed correctly
- prevented from leaking across requests/workflows
- used with explicit transaction boundaries where required

**Do not create ad-hoc database engines or sessions throughout the codebase.**

## Alembic

Use **Alembic** for database schema migrations. Database schema changes must be represented through migrations.

When changing any of the following, consider whether an Alembic migration is required:

- tables
- columns
- indexes
- constraints
- relationships
- PostgreSQL extensions
- vector-related schema

Do not manually modify production database schemas outside the migration process. Migration files should be
reviewed for correctness rather than blindly trusting autogenerated migrations.

## pgvector

The application uses **PostgreSQL + pgvector** for vector storage and similarity search. Policy documents and their
vector representations are stored in PostgreSQL. See `docs/backend/rag-pipeline.md` for the full pipeline.
